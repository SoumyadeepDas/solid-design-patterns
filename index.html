What are SOLID Principles?

SOLID is a set of five design principles coined by Robert C. Martin (Uncle Bob) that make object-oriented software easier to understand, maintain, and extend.

🏗️
Real-World Analogy
Think of SOLID like engineering rules for a skyscraper. Each floor must carry its own weight (SRP), new floors shouldn't require rebuilding the foundation (OCP), each elevator must behave like an elevator (LSP), don't force tenants to use a huge master key for every door (ISP), and electricity wiring must not depend on which specific appliance is plugged in (DIP).

01
S — Single Responsibility Principle

One Class,
One Job.

"A class should have one, and only one, reason to change."
If a class handles multiple responsibilities, a change in one area can break unrelated functionality. Each class should encapsulate a single, well-defined concern of the system.
👨‍🍳
Analogy
A chef only cooks. They don't also handle billing, clean the floor, and manage payroll. If the restaurant wants to change the billing system, that change should not affect the chef at all.

02
O — Open/Closed Principle

Open for Extension,
Closed for Modification.

"Software entities should be open for extension, but closed for modification."
Once a class is tested and working, you should be able to add new behaviour without touching existing code. This prevents regressions and keeps the system stable.
🔌
Analogy
A power strip is closed for modification (you don't rewire it), but open for extension — you can plug in a fan, a phone charger, or a lamp at any time without changing the power strip itself.
OCP — Extension via Abstraction
«interface»
Shape
+ area(): double
Circle
radius
area()
Rectangle
w, h
area()
Triangle ✨
base, h
area()
Adding Triangle never modifies existing Shape, Circle, or Rectangle classes
BAD — Java
Java 
// Adding a new shape = modifying this class!
class AreaCalculator {
    public double area(Object shape) {
        if (shape instanceof Circle) {
            Circle c = (Circle) shape;
            return Math.PI * c.radius * c.radius;
        } else if (shape instanceof Rectangle) {
            Rectangle r = (Rectangle) shape;
            return r.width * r.height;
        }
        // Want Triangle? Modify this class!
        // Every new shape = risk breaking old ones
        return 0;
    }
}
BAD — C++
C++ 
class AreaCalculator {
public:
    double area(const std::string& type,
                double a, double b = 0) {
        if (type == "circle")
            return 3.14 * a * a;
        else if (type == "rectangle")
            return a * b;
        // Adding triangle = modify here!
        return 0;
    }
};
GOOD — Java
Java 
// Interface is CLOSED. Implementations are OPEN.
interface Shape {
    double area();
}

class Circle implements Shape {
    private double radius;
    public Circle(double r) { this.radius = r; }

    public double area() {
        return Math.PI * radius * radius;
    }
}

class Rectangle implements Shape {
    private double w, h;
    public Rectangle(double w, double h)
        { this.w=w; this.h=h; }

    public double area() { return w * h; }
}

// Adding Triangle? Zero existing code modified!
class Triangle implements Shape {
    private double base, height;
    public double area() {
        return 0.5 * base * height;
    }
}

class AreaCalculator {
    public double total(List<Shape> shapes) {
        return shapes.stream()
            .mapToDouble(Shape::area).sum();
    }
}
GOOD — C++
C++ 
class Shape {
public:
    virtual double area() const = 0;
    virtual ~Shape() = default;
};

class Circle : public Shape {
    double radius;
public:
    Circle(double r) : radius(r) {}
    double area() const override {
        return 3.14159 * radius * radius;
    }
};

class Rectangle : public Shape {
    double w, h;
public:
    Rectangle(double w, double h): w(w),h(h){}
    double area() const override { return w*h; }
};

// New shape — zero old code touched!
class Triangle : public Shape {
    double base, height;
public:
    Triangle(double b, double h):base(b),height(h){}
    double area() const override {
        return 0.5 * base * height;
    }
};
✅
Key Takeaway: Use interfaces (Java) or abstract classes / pure virtual functions (C++) to define contracts. New behaviour is added via new classes, not by editing stable ones.
03
L — Liskov Substitution Principle

Subtypes Must Be
Substitutable.

"Objects of a subclass should be replaceable with objects of the parent class without breaking the application."
A child class must honour the full contract of its parent. If you replace a parent object with a child object, nothing should break — no exceptions thrown unexpectedly, no weakened guarantees.
🐦
Analogy
If you have a function that accepts any Bird and calls fly(), then a Penguin (which can't fly) violates LSP if it's a subtype of Bird. You'd need to restructure: FlyingBird and non-flying Bird are separate abstractions.
LSP Violation → Redesign
❌ Violates LSP
Bird

Penguin extends Bird
fly() → throws! 💥
→
✅ Follows LSP
Bird
eat(), sleep()
FlyingBird
fly()
Penguin
swim()
BAD — Java
Java 
class Bird {
    public void fly() {
        System.out.println("Flying!");
    }
}

// Penguin IS-A Bird but CAN'T fly
// Violates LSP — breaks the parent contract!
class Penguin extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException(
            "Penguins can't fly!");
    }
}

// Caller expects any Bird to fly
void makeBirdFly(Bird b) {
    b.fly(); // 💥 CRASHES if b is Penguin
}
GOOD — Java
Java 
interface Bird {
    void eat();
}

interface FlyingBird extends Bird {
    void fly();
}

class Eagle implements FlyingBird {
    public void eat() { System.out.println("Eating"); }
    public void fly() { System.out.println("Soaring!"); }
}

class Penguin implements Bird {
    public void eat() { System.out.println("Eating"); }
    public void swim() { System.out.println("Swimming!"); }
}

// Safe — only FlyingBird objects passed here
void makeFlyingBirdFly(FlyingBird b) {
    b.fly(); // Always safe ✅
}
GOOD — C++
C++ 
class Bird {
public:
    virtual void eat() = 0;
    virtual ~Bird() = default;
};

class FlyingBird : public Bird {
public:
    virtual void fly() = 0;
};

class Eagle : public FlyingBird {
public:
    void eat() override { /* ... */ }
    void fly() override { /* soar */ }
};

class Penguin : public Bird {
public:
    void eat() override { /* ... */ }
    void swim() { /* swim */ }
};

// Safe — compile-time enforced!
void makeFly(FlyingBird& b) {
    b.fly(); // Always safe ✅
}
⚠️
Classic LSP violation to remember:

Square extends Rectangle — A Square looks like it IS-A Rectangle, but if Rectangle has setWidth() and setHeight() independently, Square breaks that contract because both dimensions must always stay equal. This is a famous LSP trap!
✅
Key Takeaway: The rule of thumb — if it feels wrong to have a child throw an exception for an inherited method, your inheritance hierarchy is wrong. Rethink the abstraction.
04
I — Interface Segregation Principle

No Client Should
Be Forced to Depend on Methods
It Doesn't Use.

"Make fine-grained interfaces that are client-specific."
A fat interface forces implementing classes to provide stubs or empty bodies for methods they don't need. Break large interfaces into smaller, focused ones so each client only depends on what it actually uses.
🎛️
Analogy
Imagine a TV remote with 60 buttons that every device must handle — a simple table lamp shouldn't need to implement "change channel" or "adjust bass." Give the lamp its own simple switch interface.

interface Worker {
    void work();
    void eat();       // Robots don't eat!
    void manageTeam(); // Junior devs don't manage!
}

class Robot implements Worker {
    public void work() { /* OK */ }

// Segregated into focused interfaces
interface Workable   { void work(); }
interface Feedable   { void eat(); }
interface Manageable { void manageTeam(); }

class Robot implements Workable {
    public void work() {
        System.out.println("Robot working 24/7");
    }
}

// Human uses Workable + Feedable
class HumanWorker implements Workable, Feedable {
    public void work() { System.out.println("Working"); }
    public void eat()  { System.out.println("Eating"); }
}

// Manager uses all three
class Manager implements
        Workable, Feedable, Manageable {
    public void work()       { /* ... */ }
    public void eat()        { /* ... */ }
    public void manageTeam() { /* ... */ }
}
GOOD — C++
C++

public:

    virtual ~Workable() = default;
};

class Feedable {
public:
    virtual void eat() = 0;
    virtual ~Feedable() = default;
};

class Robot : public Workable {
public:

};
✅
Key Takeaway: If you find yourself writing throw new UnsupportedOperationException() in an implemented method, that's a red flag — your interface is too fat.
05
D — Dependency Inversion Principle

Depend on Abstractions,
Not Concretions.

"High-level modules should not depend on low-level modules. Both should depend on abstractions."
If your business logic class directly creates or references a specific database class, switching databases means modifying business logic — disaster! Both sides should depend on an interface/abstraction instead.
🔦
Analogy
A flashlight doesn't depend on Duracell batteries specifically — it depends on the "AA battery" interface. You can swap in any brand (Energizer, Panasonic) without modifying the flashlight. The battery slot is the abstraction.
Dependency Inversion — Depend on the Interface
❌ Tightly Coupled

directly creates ↓

save(order)
→
✅ Inverted
OrderService
processOrder()
«interface» Database

MySQLDB

save()
BAD — Java
Java 
// High-level depends on low-level directly
class MySQLDatabase {
    public void save(String data) {
        System.out.println("MySQL: saved");
    }
}

class OrderService {
    // Hard dependency on a concrete class!
    private MySQLDatabase db = new MySQLDatabase();

    public void processOrder(String order) {
        // business logic...
        db.save(order);
        // Switching to MongoDB? Modify OrderService!
    }
}
GOOD — Java
Java 
// Abstraction (interface)
interface Database {
    void save(String data);
}

// Low-level modules implement abstraction
class MySQLDatabase implements Database {
    public void save(String data) {
        System.out.println("MySQL: saved");
    }
}
class MongoDB implements Database {
    public void save(String data) {
        System.out.println("MongoDB: saved");
    }
}

// High-level depends on abstraction only
class OrderService {
    private final Database db; // Interface!

    // Injected from outside (Dependency Injection)
    public OrderService(Database db) {
        this.db = db;
    }
    public void processOrder(String order) {
        db.save(order); // Works with ANY Database!
    }
}
// Usage — swap DB with zero OrderService changes:
// new OrderService(new MySQLDatabase());
// new OrderService(new MongoDB());
GOOD — C++
C++ 
class Database {
public:
    virtual void save(const std::string& data) = 0;
    virtual ~Database() = default;
};

class MySQLDatabase : public Database {
public:
    void save(const std::string& data) override {
        std::cout << "MySQL saved: " << data << std::endl;
    }
};

class OrderService {
    Database& db; // Reference to abstraction
public:
    OrderService(Database& db) : db(db) {}

    void processOrder(const std::string& order) {
        db.save(order); // Works with any DB ✅
    }
};
✅
Key Takeaway: DIP is the backbone of Dependency Injection (DI) — a technique heavily used in Spring Boot (Java), Angular, and modern C++ architectures. Never use new ConcreteClass() inside a high-level class; inject abstractions through constructors.

Design Patterns

Proven Solutions to
Common Problems.

Design patterns are reusable blueprints for solving recurring software design challenges. They are not code — they are concepts you implement using code.

What Are Design Patterns?

In 1994, four authors (the "Gang of Four" — GoF) published Design Patterns: Elements of Reusable Object-Oriented Software. They catalogued 23 patterns across 3 categories. Think of patterns as a shared vocabulary among developers: instead of describing a whole architecture, you can say "use a Factory" and everyone understands.

🏗️ Creational
Singleton, Factory Method, Abstract Factory, Builder, Prototype
🧩 Structural
Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy
🔄 Behavioural
Observer, Strategy, Command, Iterator, Template Method, State…

1. Singleton Pattern
Creational · Ensures a class has only one instance
Relates to: SRP + DIP
"Ensure a class has only one instance, and provide a global point of access to it."
Useful for shared resources: config managers, thread pools, loggers, connection pools. Creating multiple instances would waste resources or cause inconsistencies.
🌍
Analogy
The government of a country — there's only ONE government at a time, and everyone accesses it through the same well-known entry point (the capital). You don't create a second government in parallel.
Singleton Structure
ConfigManager (Singleton)
- instance: ConfigManager (static)
- appName: String
- ConfigManager() ← private!
+ getInstance(): ConfigManager (static)
+ getConfig(key): String
All callers get the same instance object
ServiceA
getInstance()
ServiceB
getInstance()
ServiceC
getInstance()
↑ All return the same object in memory
Java — Thread-Safe Singleton
Java 
public class ConfigManager {

    // volatile → ensures visibility across threads
    private static volatile ConfigManager instance;

    // private constructor → prevents new ConfigManager()
    private ConfigManager() {
        System.out.println("Loading config...");
    }

    // Double-checked locking (thread-safe + fast)
    public static ConfigManager getInstance() {
        if (instance == null) {
            synchronized (ConfigManager.class) {
                if (instance == null) {
                    instance = new ConfigManager();
                }
            }
        }
        return instance;
    }

    public String getDbUrl() {
        return "jdbc:mysql://localhost/mydb";
    }
}

// Usage:
ConfigManager cfg = ConfigManager.getInstance();
String url = cfg.getDbUrl();
// ConfigManager.getInstance() always returns THE SAME object
C++ — Thread-Safe Singleton
C++ 
#include <mutex>
#include <string>
#include <iostream>

class ConfigManager {
private:
    static ConfigManager* instance;
    static std::mutex mtx;

    // Private constructor
    ConfigManager() {
        std::cout << "Loading config...\n";
    }

public:
    // Delete copy constructor and assignment
    ConfigManager(const ConfigManager&) = delete;
    ConfigManager& operator=(const ConfigManager&) = delete;

    static ConfigManager* getInstance() {
        std::lock_guard<std::mutex> lock(mtx);
        if (!instance)
            instance = new ConfigManager();
        return instance;
    }

    std::string getDbUrl() {
        return "mysql://localhost/mydb";
    }
};

// Definitions (in .cpp)
ConfigManager* ConfigManager::instance = nullptr;
std::mutex ConfigManager::mtx;
🔗
SOLID Link: Singleton can violate SRP if it does too much. Pair it with DIP — inject the singleton as an interface so tests can swap it out easily.

2. Factory Method Pattern
Creational · Delegates object creation to subclasses
Relates to: OCP + DIP
"Define an interface for creating an object, but let subclasses decide which class to instantiate."
Instead of calling new Foo() directly, you call a factory method. The caller doesn't know or care about the concrete class — it just uses the interface. Adding new types requires only a new factory, not modifying existing code (OCP).
🍕
Analogy
A pizza store (creator) has a "createPizza()" factory method. The NY branch creates NY-style pizzas; the Chicago branch creates deep-dish ones. The customer just orders "a pizza" — they don't control the construction details.

→ new EmailNotif()

Java — Factory Method
Java 
// Product interface
interface Notification {
    void send(String msg);
}

// Concrete products
class EmailNotification implements Notification {
    public void send(String msg) {
        System.out.println("Email: " + msg);
    }
}
class SMSNotification implements Notification {
    public void send(String msg) {
        System.out.println("SMS: " + msg);
    }
}

// Abstract creator
abstract class NotificationFactory {
    public abstract Notification createNotification();

    // Template method uses factory method
    public void notify(String msg) {
        Notification n = createNotification();
        n.send(msg);
    }
}

// Concrete creators
class EmailFactory extends NotificationFactory {
    public Notification createNotification() {
        return new EmailNotification();
    }
}
class SMSFactory extends NotificationFactory {
    public Notification createNotification() {
        return new SMSNotification();
    }
}

// Client code — decoupled from concrete classes
NotificationFactory factory = new EmailFactory();
factory.notify("Order confirmed!");
// Swap to SMS: new SMSFactory() — zero other changes
C++ — Factory Method
C++ 
class Notification {
public:
    virtual void send(const std::string& msg) = 0;
    virtual ~Notification() = default;
};

class EmailNotification : public Notification {
public:
    void send(const std::string& msg) override {
        std::cout << "Email: " << msg << "\n";
    }
};

class NotificationFactory {
public:
    virtual std::unique_ptr<Notification>
    createNotification() = 0;
    virtual ~NotificationFactory() = default;

    void notify(const std::string& msg) {
        auto n = createNotification();
        n->send(msg);
    }
};

class EmailFactory : public NotificationFactory {
public:
    std::unique_ptr<Notification>
    createNotification() override {
        return std::make_unique<EmailNotification>();
    }
};
🔗
SOLID Link: Factory Method enforces OCP — new product types are added via new factories without modifying existing ones. It also supports DIP since clients depend on the abstract factory and product interfaces, not concrete classes.

3. Observer Pattern
Behavioural · One-to-many event notification
Relates to: OCP + ISP
"Define a one-to-many dependency so that when one object changes state, all dependents are notified and updated automatically."
The Subject (publisher) knows nothing about its Observers (subscribers) except that they implement the Observer interface. This is the foundation of event-driven programming, reactive systems, and Java's EventListener.
📱
Analogy
A YouTube channel (Subject) doesn't personally contact each subscriber when a video is uploaded. It simply notifies all subscribers at once. Subscribers (Observers) decide individually what to do — watch now, watch later, ignore.
Observer Pattern Flow

When price changes → all observers are automatically notified
Java — Observer Pattern
Java 
import java.util.*;

// Observer interface
interface Observer {
    void update(double price);
}

// Subject interface
interface Subject {
    void addObserver(Observer o);
    void removeObserver(Observer o);
    void notifyObservers();
}

// Concrete Subject
class StockMarket implements Subject {
    private List<Observer> observers = new ArrayList<>();
    private double price;

    public void setPrice(double price) {
        this.price = price;
        notifyObservers(); // auto-notify on change!
    }
    public void addObserver(Observer o) { observers.add(o); }
    public void removeObserver(Observer o) { observers.remove(o); }
    public void notifyObservers() {
        observers.forEach(o -> o.update(price));
    }
}

// Concrete Observers
class MobileApp implements Observer {
    public void update(double price) {
        System.out.println("📱 App: Price = $" + price);
    }
}
class EmailAlert implements Observer {
    public void update(double price) {
        System.out.println("📧 Email: Price = $" + price);
    }
}

// Usage
StockMarket market = new StockMarket();
market.addObserver(new MobileApp());
market.addObserver(new EmailAlert());
market.setPrice(150.75); // Both notified automatically!
C++ — Observer Pattern
C++ 
#include <vector>
#include <iostream>

class Observer {
public:
    virtual void update(double price) = 0;
    virtual ~Observer() = default;
};

class StockMarket {
    std::vector<Observer*> observers;
    double price = 0;
public:
    void addObserver(Observer* o) {
        observers.push_back(o);
    }
    void setPrice(double p) {
        price = p;
        for (auto* o : observers) o->update(price);
    }
};

class MobileApp : public Observer {
public:
    void update(double price) override {
        std::cout << "App: $" << price << "\n";
    }
};
🔗
SOLID Link: Observer satisfies OCP — add new observers without changing the Subject. It uses ISP by defining small, focused Observer/Subject interfaces. This is how Java's EventListener and Spring's ApplicationEvent work internally.

4. Strategy Pattern
Behavioural · Swap algorithms at runtime
Relates to: OCP + DIP
"Define a family of algorithms, encapsulate each one, and make them interchangeable."
Instead of hard-coding an algorithm into a class, you extract it into a strategy object. The context class delegates the work to whichever strategy it holds. You can change strategies at runtime without modifying the context.
🗺️
Analogy
Google Maps lets you pick your travel strategy — car, bike, walking, or transit. The destination doesn't change; only the routing algorithm does. The app delegates routing to the chosen strategy and displays the result.

    public void pay(double amount) {
        System.out.println("📲 Paid $" + amount + " via UPI");
    }
}

// Context
class ShoppingCart {
    private PaymentStrategy strategy;

    public void setPaymentStrategy(PaymentStrategy s) {
        this.strategy = s;
    }
    public void checkout(double amount) {
        strategy.pay(amount); // delegates to strategy
    }
}

// Usage — swap at runtime!
ShoppingCart cart = new ShoppingCart();
cart.setPaymentStrategy(new CreditCardPayment());
cart.checkout(99.99); // 💳 Paid $99.99 via Credit Card

cart.setPaymentStrategy(new UPIPayment());
cart.checkout(49.99); // 📲 Paid $49.99 via UPI
C++ — Strategy Pattern
C++ 
class PaymentStrategy {
public:
    virtual void pay(double amount) = 0;
    virtual ~PaymentStrategy() = default;
};

class CreditCardPayment : public PaymentStrategy {
public:
    void pay(double amt) override {
        std::cout << "Card: $" << amt << "\n";
    }
};

class ShoppingCart {
    PaymentStrategy* strategy = nullptr;
public:
    void setStrategy(PaymentStrategy* s) {
        strategy = s;
    }
    void checkout(double amount) {
        if (strategy) strategy->pay(amount);
    }
};
🔗
SOLID Link: Strategy embodies OCP (add new strategies without modifying the context) and DIP (context depends on the abstract PaymentStrategy, not a concrete implementation). It's commonly used in Java's Comparator, sorting algorithms, and compression systems.

5. Decorator Pattern
Structural · Add behaviour dynamically without subclassing
Relates to: OCP + SRP
"Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality."
Each decorator wraps another object and adds one small behaviour. You can stack decorators like layers — adding logging, compression, encryption, or caching without touching the original class.
☕
Analogy
Order a coffee at Starbucks: start with an Espresso, add a Milk decorator (+₹20), add a Sugar decorator (+₹10), add a Whip decorator (+₹15). Each topping wraps the previous and adds its cost. The base espresso never changes.
Decorator Wrapping — Coffee Example
WhipDecorator (outermost)
wraps → MilkDecorator
getCost() → inner.getCost() + 15
MilkDecorator
wraps → Espresso
getCost() → inner.getCost() + 20
Espresso (base)
getCost() → 100
Total: 100 + 20 + 15 = ₹135
Java — Decorator Pattern
Java 
// Component interface
interface Coffee {
    String getDescription();
    double getCost();
}

// Concrete component
class Espresso implements Coffee {
    public String getDescription() { return "Espresso"; }
    public double getCost() { return 100; }
}

// Abstract decorator
abstract class CoffeeDecorator implements Coffee {
    protected final Coffee coffee;
    public CoffeeDecorator(Coffee c) { this.coffee = c; }
}

// Concrete decorators — each adds ONE thing
class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee c) { super(c); }
    public String getDescription() {
        return coffee.getDescription() + ", Milk";
    }
    public double getCost() { return coffee.getCost() + 20; }
}
class WhipDecorator extends CoffeeDecorator {
    public WhipDecorator(Coffee c) { super(c); }
    public String getDescription() {
        return coffee.getDescription() + ", Whip";
    }
    public double getCost() { return coffee.getCost() + 15; }
}

// Usage — stack decorators!
Coffee order = new Espresso();        // ₹100
order = new MilkDecorator(order);  // ₹120
order = new WhipDecorator(order);  // ₹135
System.out.println(order.getDescription()); // Espresso, Milk, Whip
System.out.println(order.getCost());        // 135.0
C++ — Decorator Pattern
C++ 
class Coffee {
public:
    virtual std::string getDescription() = 0;
    virtual double getCost() = 0;
    virtual ~Coffee() = default;
};

class Espresso : public Coffee {
public:
    std::string getDescription() override {
        return "Espresso";
    }
    double getCost() override { return 100; }
};

class MilkDecorator : public Coffee {
    std::unique_ptr<Coffee> coffee;
public:
    MilkDecorator(std::unique_ptr<Coffee> c)
        : coffee(std::move(c)) {}

    std::string getDescription() override {
        return coffee->getDescription() + ", Milk";
    }
    double getCost() override {
        return coffee->getCost() + 20;
    }
};

// Usage
auto order = std::make_unique<Espresso>();
order = std::make_unique<MilkDecorator>(
    std::move(order));
std::cout << order->getCost(); // 120
🔗
SOLID Link: Decorator follows OCP — you add new behaviours (decorators) without touching the base class. Each decorator has SRP — it does exactly one thing. Java's BufferedReader wrapping FileReader is a classic Decorator in the JDK!

6. Adapter Pattern
Structural · Make incompatible interfaces work together
Relates to: DIP + OCP
"Convert the interface of a class into another interface that clients expect."
Like a power adapter that lets a US plug work in a European socket — the Adapter pattern lets an existing class work with code expecting a different interface. Invaluable when integrating legacy systems or third-party libraries.
🗂️
Analogy
Your new music player expects audio in MP3 format. You have a legacy library that only provides WAV files. An AudioAdapter sits in between, converting WAV → MP3 so both sides remain unchanged.
Adapter Pattern Flow
Client
uses MediaPlayer
«i» MediaPlayer
play(file)
MediaAdapter ✨
wraps LegacyPlayer
play() → legacy.playWav()
LegacyPlayer
playWav(file)
Java — Adapter Pattern
Java 
// Target interface (what client expects)
interface MediaPlayer {
    void play(String file);
}

// Adaptee — legacy class we can't modify
class LegacyAudioPlayer {
    public void playWav(String file) {
        System.out.println("Playing WAV: " + file);
    }
}

// Adapter — bridges the gap!
class MediaAdapter implements MediaPlayer {
    private final LegacyAudioPlayer legacyPlayer;

    public MediaAdapter(LegacyAudioPlayer player) {
        this.legacyPlayer = player;
    }

    public void play(String file) {
        // Translate: play() → playWav()
        legacyPlayer.playWav(file);
    }
}

// Client — uses MediaPlayer interface only
class AudioApp {
    private final MediaPlayer player;

    public AudioApp(MediaPlayer player) {
        this.player = player;
    }
    public void run() {
        player.play("song.wav"); // Doesn't know about LegacyPlayer!
    }
}

// Usage
LegacyAudioPlayer legacy = new LegacyAudioPlayer();
MediaPlayer adapter = new MediaAdapter(legacy);
new AudioApp(adapter).run(); // Playing WAV: song.wav
C++ — Adapter Pattern
C++ 
// Target (expected interface)
class MediaPlayer {
public:
    virtual void play(const std::string& f) = 0;
    virtual ~MediaPlayer() = default;
};

// Adaptee — can't modify this
class LegacyAudioPlayer {
public:
    void playWav(const std::string& f) {
        std::cout << "WAV: " << f << "\n";
    }
};

// Adapter — translates interface
class MediaAdapter : public MediaPlayer {
    LegacyAudioPlayer& legacy;
public:
    MediaAdapter(LegacyAudioPlayer& l) : legacy(l) {}

    void play(const std::string& f) override {
        legacy.playWav(f); // translate the call
    }
};

// Client
void runApp(MediaPlayer& p) {
    p.play("song.wav"); // ✅ Works!
}
🔗
SOLID Link: Adapter enforces DIP (client depends on MediaPlayer abstraction, not LegacyPlayer). It enables OCP — you integrate a new third-party library via a new adapter, leaving existing code untouched. Used constantly in Spring's data access layer.
